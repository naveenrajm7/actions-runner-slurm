The initial release intentionally supports a narrow, verifiable deployment model.

## Execution

- Pyxis/Enroot container and VMoCS VM execution are implemented. Only Pyxis has completed an end-to-end GitHub workflow validation so far.
- Native host execution is not implemented, even though the evolving configuration schema reserves a `native` value.
- Each runner allocation must request exactly one node and one task.
- The supplied container image and documented initial VM guest contract use Linux x86-64.
- Docker container actions, job containers, service containers, and Docker-in-Docker are not supported.
- The image and mount paths are controlled by the cluster administrator, not by workflow labels.

## Security and tenancy

- The supported trust boundary is private, trusted repositories.
- Pyxis/Enroot and VMoCS are not treated as complete hostile multi-tenant sandboxes by this project.
- Workflow code runs as the configured Slurm identity and inherits its reachable services and explicit mounts.
- Claim credentials are passed through the Slurm job environment and may be visible to sufficiently privileged Slurm users or administrators.
- VMoCS forwards only named variables into the guest command, but runner `_diag` files are not yet exported from the disposable VM.

## Availability and operations

- One process owns one BoltDB state file; active-active high availability is not supported.
- Metrics and a drain-administration API are not implemented.
- The service does not create GitHub runner groups or manage their repository policies.
- Fast-finished allocation accounting fallback and the full failure/concurrency campaign remain future work.
- The `v0.0.42` batched job endpoint is the verified reconciliation contract.

## Resource selection

- Every scale-set name maps to one fixed Slurm resource template.
- Unknown labels do not create runner classes.
- Dynamic per-workflow CPU, memory, walltime, partition, account, QOS, and GRES requests are not supported.

These boundaries should be treated as deployment requirements, not merely missing documentation. Future releases may expand them without changing the secure defaults of existing installations.
