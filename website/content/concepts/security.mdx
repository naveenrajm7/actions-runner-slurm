The initial security boundary assumes trusted private repositories, a dedicated Unix and Slurm identity, restricted GitHub runner groups, and carefully selected mounts.

<Note variant="warning">
  Pyxis/Enroot and VMoCS provide disposable environments, not a complete hostile multi-tenant boundary. Workflow code retains the access granted through the Slurm identity, selected backend, devices, storage, and network.
</Note>

## Long-lived credentials

The service reads three sensitive files:

- The GitHub App private key.
- The Slurm JWT.
- The JIT response encryption key.

Each file must be readable by the service identity and must not be group- or world-accessible. Store secrets outside the repository and outside the runner image. The configuration contains only absolute paths.

The Slurm JWT is re-read for every REST request, allowing atomic renewal. The GitHub App key and JIT encryption key are loaded at process startup and require a restart after replacement.

## Per-allocation claim

Before submission, the service creates a random 256-bit claim credential and stores only its SHA-256 digest. The plaintext travels in the Slurm job environment and authorizes one lease until registration, terminal state, or expiry.

Administrators and users who can inspect another job's environment may be able to see this credential. Slurm visibility and process inspection must therefore be restricted according to the site's trust model.

The service returns JIT data only after verifying the claim, job ID, cluster when available, correlation comment, allocation phase, and restart count. Retryable JIT content is encrypted with AES-256-GCM in the state database and bound to the lease ID.

## TLS

The runner callback always uses HTTPS. TLS verification cannot be disabled. For a private CA, Pyxis mounts `service.tls.caFile` read-only into the allocation. A VMoCS guest must contain that CA at `/etc/slurm-gha/callback-ca.crt`. The bootstrap passes the applicable path explicitly to `curl`.

Use HTTPS for `slurmrestd` as well. Configure `slurm.caFile` for a private Slurm CA; `slurm.insecureSkipVerify: true` is rejected.

## Filesystem exposure

In Pyxis mode, the launcher disables the home mount and container entrypoint by default. It creates a fresh private runner directory and removes it after the allocation step. Diagnostics are copied to the configured log directory.

Keep `mountHome: false`. Add `extraMounts` only after reviewing what untrusted workflow commands could read or modify. Prefer read-only mounts and dedicated, narrowly scoped data paths. In VMoCS mode, filesystem and device exposure comes from the site-managed template; the Actions Runner Slurm configuration does not add dynamic VM mounts.

## GitHub access policy

Use a dedicated runner group with selected-repository access and keep public repository access disabled. A pull request from a fork can cause workflow code to execute if repository and workflow policy allow it; runner-group selection alone does not make public workflows safe.
