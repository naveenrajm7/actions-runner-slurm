## Verified behavior

The development cluster verified:

- REST submission, batched job listing, state observation, and cancellation.
- A one-node, one-task allocation launched from a shared SquashFS image.
- Pyxis startup with the home and image entrypoint disabled.
- Compute-node DNS resolution and TCP/443 access to GitHub.
- A private-CA HTTPS callback from a compute allocation to the service.
- GitHub App installation authentication and organization runner-group access.
- Complete private-repository workflows in both Pyxis and VMoCS modes using `runs-on: slurm-cpu-small`.
- JIT claim, ephemeral runner registration, repository checkout, job completion, runner deregistration, and Slurm cleanup.

On October 8, 2026, VMoCS 0.1.3 and the corrected SPANK plugin passed repeated selected-variable forwarding. A REST smoke then booted template `actions-runner-ubuntu-24.04` with 2 vCPUs, validated runner `2.337.0`, its matching bootstrap, GitHub egress, and the callback CA baked at `/etc/slurm-gha/callback-ca.crt`.

A live integration job used the production renderer and claim handler, authenticated over HTTPS, obtained a real GitHub JIT configuration, and brought an ephemeral runner to `Listening for Jobs`.

A push-triggered workflow in a selected private repository then completed the VMoCS path. The listener submitted a Slurm allocation, the VM claimed and registered an ephemeral runner, and the validation job succeeded. Slurm recorded `COMPLETED`, exit code `0:0`; the runner deregistered automatically and no allocation remained queued.

## REST endpoint behavior

The verified deployment's singular `/job/{id}` v0.0.42 handler rejects federation-encoded IDs above the local `MAX_JOB_ID`. The adapter therefore uses plural `GET /jobs/` for full-record reconciliation and plural `DELETE /jobs/` with an exact job list and explicit `SIGKILL` for cancellation. A forced-timeout job verified that the plural REST path cancels a federated allocation without native fallback.

This is measured behavior from one deployment, not a claim that every Slurm version behaves the same way. Validate another site with `doctor`, `slurm-smoke`, and a disposable end-to-end workflow before production use.

For raw evidence and image checksums, see the repository's [compatibility record](https://github.com/naveenrajm7/actions-runner-slurm/blob/main/docs/compatibility.md).
